# Формат `.darc`

`.darc` — самодостаточный контейнер DedupArc. Формат хранит одинаковые блоки данных один раз, а структуру файлов — в каталоге в конце архива.

DedupArc 1.0 создаёт формат версии 2 и продолжает читать формат версии 1.

## Общая схема версии 2

```text
+----------------------------------+
| DARC header                      |
+----------------------------------+
| CHNK unique data block #1        |
+----------------------------------+
| CHNK unique data block #2        |
+----------------------------------+
| ...                              |
+----------------------------------+
| MNF2 compressed archive catalog  |
+----------------------------------+
| DEND catalog offset + SHA-256    |
+----------------------------------+
```

Числа записываются в little-endian.

## Заголовок

8 байт:

```text
44 41 52 43 00 01 0D 0A
D  A  R  C     1  \r \n
```

Сигнатура контейнера пока сохраняется общей для v1 и v2. Версия структуры определяется полем `version` каталога.

## Запись данных

```text
4 bytes   "CHNK"
32 bytes  SHA-256 исходных данных
4 bytes   исходный размер, uint32
4 bytes   сохранённый размер, uint32
1 byte    метод: 0 = raw, 1 = zlib
N bytes   данные
```

Блок с конкретным SHA-256 физически записывается один раз.

## Крупные файлы

Файлы крупнее порога мелких файлов режутся BuzHash CDC со стандартными параметрами:

- минимум: 64 КиБ;
- средний размер: 256 КиБ;
- максимум: 1 МиБ.

Граница ставится после минимального размера, когда скользящий хэш попадает под маску среднего размера, либо принудительно на максимальном размере.

Каждая запись файла хранит упорядоченный список SHA-256 логических блоков.

CDC нужен для того, чтобы небольшая вставка или удаление внутри файла не меняли границы всех последующих блоков.

## Мелкие файлы

По умолчанию файл размером до 256 КиБ не получает отдельную физическую запись `CHNK`.

Небольшие файлы группируются по типу содержимого и добавляются в общий блок примерно до 16 МиБ. Для каждого файла каталог хранит:

```text
chunk   SHA-256 общего блока
offset  смещение файла внутри блока
length  длина файла
```

Одинаковые мелкие файлы переиспользуют одну и ту же ссылку на диапазон общего блока. Отдельный SHA-256 такого файла в каталоге не хранится: целостность его байтов задаётся SHA-256 общего блока, а смещение и длина входят в защищённый SHA-256 каталога.

Такой подход уменьшает:

- количество физических записей в архиве;
- накладные расходы zlib на тысячи коротких потоков;
- размер служебной информации;
- время создания и проверки наборов с большим количеством мелких файлов.

## Сжатие данных

В v2 доступны три профиля:

- `fast` — zlib level 1 для обычных блоков и level 3 для общих блоков мелких файлов;
- `balanced` — zlib level 8 для обычных блоков и level 9 для общих блоков мелких файлов;
- `maximum` — zlib level 9 для всех блоков.

Для форматов, которые обычно уже содержат сжатые данные, DedupArc сначала оценивает энтропию и может сразу сохранить блок как `raw`. Для остальных данных сжатие выполняется и принимается только если фактический результат становится меньше исходного блока.

Такой подход не жертвует коэффициентом сжатия обычных бинарных данных только из-за грубой оценки энтропии.

## Каталог архива v2

Каталог остаётся JSON внутри реализации, но в контейнер записывается в сжатом виде.

```text
4 bytes   "MNF2"
8 bytes   сохранённый размер, uint64
8 bytes   исходный размер JSON, uint64
1 byte    метод: 0 = raw, 1 = zlib
N bytes   каталог
```

SHA-256 в footer считается от распакованного JSON-каталога.

Это позволяет быстро получить список файлов с конца архива и при этом не раздувать контейнер на деревьях с десятками или сотнями тысяч записей.

## Каталог архива v1

Старый формат остаётся читаемым:

```text
4 bytes   "MNFT"
8 bytes   размер JSON, uint64
N bytes   UTF-8 JSON
```

Файлы v1 используют только списки CDC-блоков и не содержат ссылок на общие блоки мелких файлов.

## Footer

Последние 44 байта архива:

```text
4 bytes   "DEND"
8 bytes   смещение MNFT/MNF2, uint64
32 bytes  SHA-256 распакованного JSON-каталога
```

Благодаря footer список файлов можно прочитать без прохода по всем блокам данных.

## Проверка

Полная проверка включает:

1. SHA-256 каталога;
2. корректность границ всех физических блоков;
3. распаковку и SHA-256 каждого уникального блока;
4. наличие всех блоков, на которые ссылаются файлы;
5. проверку диапазонов файлов внутри общих блоков;
6. размер каждого восстановленного файла; для обычных CDC-файлов дополнительно проверяется их полный SHA-256.

Для мелкого файла из общего блока отдельный файловый SHA-256 избыточен: блок уже проверяется по SHA-256, а ссылка на его диапазон защищена хэшем каталога.

Для общих блоков Reader использует ограниченный LRU-кэш распакованных данных. Это не меняет формат, но не позволяет тысяче мелких файлов заставить проверку или распаковку повторно распаковывать один и тот же 16-МиБ блок.
