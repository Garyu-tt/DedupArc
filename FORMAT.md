# Формат `.darc`

`.darc` — самодостаточный контейнер DedupArc. Формат хранит одинаковые блоки данных один раз, а структуру файлов — в каталоге в конце архива.

По умолчанию DedupArc 1.1 создаёт формат версии 2 и продолжает читать формат версии 1.
Экспериментальные режимы: `--extreme` пишет **v3**, `--neutron` пишет **v4**, `--neutron-dag` пишет **v5**. Остальные режимы остаются в v2.

## Общая схема версий 2, 3 и 4

```text
+----------------------------------+
| DARC header                      |
+----------------------------------+
| CHNK unique data block #1        |
+----------------------------------+
| CHNK unique data block #2        |
+----------------------------------+
| ...                              |
+----------------------------------+
| MNF2 compressed archive catalog  |
+----------------------------------+
| DEND catalog offset + SHA-256    |
+----------------------------------+
```

Числа записываются в little-endian.

## Заголовок

8 байт:

```text
44 41 52 43 00 01 0D 0A
D  A  R  C     1  \r \n
```

Сигнатура контейнера пока сохраняется общей для v1 и v2. Версия структуры определяется полем `version` каталога.

## Запись данных

```text
4 bytes   "CHNK"
32 bytes  SHA-256 исходных данных
4 bytes   исходный размер, uint32
4 bytes   сохранённый размер, uint32
1 byte    метод: 0 = raw, 1 = zlib, 2 = delta-zlib (v3/v4), 3 = math bytecode (v4/v5), 4 = math-root ref (только v5)
N bytes   данные
```

Блок с конкретным SHA-256 физически записывается один раз.

## Дельта-блоки в версии 3 (Extreme R01)

Режим `deduparc create --extreme` записывает обычные блоки (`raw` или `zlib`),
а для **похожих, но не идентичных** блоков может выбрать метод `2`:

```text
CHNK header (обычные 45 байт, method=2)
32 bytes  SHA-256 базового блока в том же архиве
N bytes   zlib( XOR(данные_нового_блока, данные_базового_блока) )
```

В поле stored size включаются 32 байта SHA-256 базы. Размер базы должен
совпадать с исходным размером нового блока. База всегда расположена ранее
дельты и сама использует только raw/zlib. Таким образом, цепочек дельт,
зацикливания и обращения к внешним файлам нет. SHA-256 восстановленного
блока проверяется как обычно.

- Поиск сходства: восемь 64-байтовых образцов на позиции блока, совпадение по SHA-256 первых 64 бит,
  а затем обязательная точная оценка всех различий.
- Минимальный/максимальный размер кандидата: 64 КиБ / 1 МиБ.
- Память словаря кандидатов: до 64 МиБ плюс индекс; не более четырёх
  кандидатов на отпечаток.
- Дельта принимается только если её **полный физический размер** минимум
  на 64 байта лучше альтернативного raw/zlib; в противном случае записывается
  обычный блок.
- Дельта является полностью lossless, не опирается на предсказания или
  приближённое восстановление.

Формат v3 читается DedupArc 1.1+. Более старые версии программы могут
отклонить v3. По умолчанию архивы по-прежнему сохраняются как v2.

## Математические блоки в версии 4 (Neutron R02)

Режим `create --neutron` может использовать метод 3. Длина исходного блока
уже известна из поля `CHNK.rawSize`; байт-код описывает генератор и
отсортированные точные исключения:

```text
1 byte   opcode: A0=constant; A1=affine mod 256; A2=periodic
params   A0: value; A1: start,step; A2: period(1..32), period-bytes
uvarint  number of patches
repeat   uvarint gap from previous patch end, 1 byte exact replacement
```

Начальный previous patch end = 0, после замены на индексе i становится i+1.
Дубликаты позиций, превышение исходной длины, переполнение varint,
недопустимые opcodes, посторонние байты и неверный SHA-256 отвергаются.
Размер блоков math ограничен 32 МиБ; запись выбирается лишь при реальном
выигрыше не менее 16 байт относительно raw/zlib. Математический блок
может быть базой для XOR-дельты, но не наоборот.

Это lossless-представление, а не альтернативная 16-ричная физическая
память. Декодер применяет только детерминированную арифметику байтов.

## Математические ссылки в версии 5 (Neutron R03)

Метод CHNK=4 хранит **uvarint-порядковый номер ранее записанного
математического блока (метод=3)**, затем uvarint-количество точных
замен, затем отсортированные пары `(gap:uvarint, value:byte)` по
правилам v4. База должна иметь тот же исходный размер, быть физически
раньше ссылки и не может быть ссылкой либо дельтой. Глубина графа — 1.
Неизвестные корни, циклы, повреждённые varint, слишком большие размеры
и лишние байты отклоняются, результат сверяется с SHA-256 блока.

Запись только через `--neutron-dag`; старые режимы и их форматы не изменяются.
Подробнее: [NEUTRON_R03.md](docs/NEUTRON_R03.md).

## Крупные файлы

Файлы крупнее порога мелких файлов режутся BuzHash CDC со стандартными параметрами:

- минимум: 64 КиБ;
- средний размер: 256 КиБ;
- максимум: 1 МиБ.

Граница ставится после минимального размера, когда скользящий хэш попадает под маску среднего размера, либо принудительно на максимальном размере.

Каждая запись файла хранит упорядоченный список SHA-256 логических блоков.

CDC нужен для того, чтобы небольшая вставка или удаление внутри файла не меняли границы всех последующих блоков.

## Мелкие файлы

По умолчанию файл размером до 256 КиБ не получает отдельную физическую запись `CHNK`.

Небольшие файлы группируются по типу содержимого и добавляются в общий блок примерно до 16 МиБ. Для каждого файла каталог хранит:

```text
chunk   SHA-256 общего блока
offset  смещение файла внутри блока
length  длина файла
```

Одинаковые мелкие файлы переиспользуют одну и ту же ссылку на диапазон общего блока. Отдельный SHA-256 такого файла в каталоге не хранится: целостность его байтов задаётся SHA-256 общего блока, а смещение и длина входят в защищённый SHA-256 каталога.

Такой подход уменьшает:

- количество физических записей в архиве;
- накладные расходы zlib на тысячи коротких потоков;
- размер служебной информации;
- время создания и проверки наборов с большим количеством мелких файлов.

## Сжатие данных

В v2 доступны три профиля:

- `fast` — zlib level 1 для обычных блоков и level 3 для общих блоков мелких файлов;
- `balanced` — zlib level 8 для обычных блоков и level 9 для общих блоков мелких файлов;
- `maximum` — zlib level 9 для всех блоков;
- `extreme` — zlib level 9 + адаптивная дельта-кодировка (версия 3).
- `neutron` — zlib level 9 + математический байт-код + адаптивные дельты (версия 4).

Для форматов, которые обычно уже содержат сжатые данные, DedupArc сначала оценивает энтропию и может сразу сохранить блок как `raw`. Для остальных данных сжатие выполняется и принимается только если фактический результат становится меньше исходного блока.

Такой подход не жертвует коэффициентом сжатия обычных бинарных данных только из-за грубой оценки энтропии.

## Каталог архива v2

Каталог остаётся JSON внутри реализации, но в контейнер записывается в сжатом виде.

```text
4 bytes   "MNF2"
8 bytes   сохранённый размер, uint64
8 bytes   исходный размер JSON, uint64
1 byte    метод: 0 = raw, 1 = zlib, 2 = delta-zlib (v3/v4), 3 = math bytecode (v4)
N bytes   каталог
```

SHA-256 в footer считается от распакованного JSON-каталога.

Это позволяет быстро получить список файлов с конца архива и при этом не раздувать контейнер на деревьях с десятками или сотнями тысяч записей.

## Каталог архива v1

Старый формат остаётся читаемым:

```text
4 bytes   "MNFT"
8 bytes   размер JSON, uint64
N bytes   UTF-8 JSON
```

Файлы v1 используют только списки CDC-блоков и не содержат ссылок на общие блоки мелких файлов.

## Footer

Последние 44 байта архива:

```text
4 bytes   "DEND"
8 bytes   смещение MNFT/MNF2, uint64
32 bytes  SHA-256 распакованного JSON-каталога
```

Благодаря footer список файлов можно прочитать без прохода по всем блокам данных.

## Проверка

Полная проверка включает:

1. SHA-256 каталога;
2. корректность границ всех физических блоков;
3. распаковку и SHA-256 каждого уникального блока;
4. наличие всех блоков, на которые ссылаются файлы;
5. проверку диапазонов файлов внутри общих блоков;
6. размер каждого восстановленного файла; для обычных CDC-файлов дополнительно проверяется их полный SHA-256.

Для мелкого файла из общего блока отдельный файловый SHA-256 избыточен: блок уже проверяется по SHA-256, а ссылка на его диапазон защищена хэшем каталога.

Для общих блоков Reader использует ограниченный LRU-кэш распакованных данных. Это не меняет формат, но не позволяет тысяче мелких файлов заставить проверку или распаковку повторно распаковывать один и тот же 16-МиБ блок.
